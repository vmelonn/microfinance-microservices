Microfinance Practice Schema

Thirteen tables, 9,000 transactions, a year of history. The keys, how they connect, and the three shapes that make joins worth practising.

foreign key the two unusual shapes: self-reference and many-to-many PK primary key FK foreign key

How to read it

An arrow points from the table holding the foreign key to the table holding the primary key it references. So accounts.user_id → users means each account names one user, and one user can have many accounts. The arrow always points at the "one" side.

Three tables carry the load. accounts is the hub every identity path arrives at, transactions is where every event is recorded, and ledger_entries is the only place money actually lives. Most queries you write will pass through at least two of them.

The three shapes worth understanding

1. The self-reference: branches

parent_branch_id points back at branches. One row has NULL there, and that row is head office. Below it sit four regional hubs, and below those ten local branches: three levels, discovered rather than hard-coded, which is what a recursive CTE is for. 

-- walk the tree, depth and all
WITH RECURSIVE tree AS (
    SELECT branch_id, name, 0 AS depth
    FROM branches WHERE parent_branch_id IS NULL
    UNION ALL
    SELECT b.branch_id, b.name, tree.depth + 1
    FROM branches b JOIN tree ON b.parent_branch_id = tree.branch_id
)
SELECT depth, name FROM tree ORDER BY depth, name;

2. The many-to-many: dispute_tags

A dispute carries several tags; a tag applies to many disputes. Neither table can hold the other's key, so a third table holds both. Its primary key is the pair, which is what stops the same tag being attached twice. Reaching tags from disputes always costs two joins.

3. The mutually exclusive keys: transactions

agent_id is set on all 2,719 top-ups and nothing else. merchant_id is set on all 4,972 purchases and nothing else. Transfers have neither. This is not untidiness: a cash-in and a card purchase genuinely have different counterparties.

The trap. An inner join on agent_id silently discards every purchase and every transfer, because NULL matches nothing. You get a confident answer about a third of the table.

Join recipes

The paths you will retype most. Copy them rather than rederiving each time.

from → tojoin
transaction → who paid JOIN ledger_entries e ON e.rrn = t.rrn AND e.entry_type = 'debit'
entry → the person JOIN accounts a ON a.account_id = e.account_id JOIN users u ON u.user_id = a.user_id
purchase → category JOIN merchants m ON m.merchant_id = t.merchant_id JOIN merchant_categories c ON c.category_id = m.category_id
top-up → branch JOIN agents ag ON ag.agent_id = t.agent_id JOIN branches b ON b.branch_id = ag.branch_id
dispute → tags JOIN dispute_tags dt ON dt.dispute_id = d.dispute_id JOIN tags g ON g.tag_id = dt.tag_id
account → balance sum(CASE WHEN entry_type = 'credit' THEN amount_cents ELSE -amount_cents END)

Five rules to keep beside you

1Filter status = 'approved' on transactions unless you specifically want the failures. 1,867 rows moved no money.
2Money is integer cents. Divide by 100.0, not 100, or integer division truncates.
3IS NULL, never = NULL. Comparing to NULL is unknown, and unknown rows are dropped.
4On a LEFT JOIN, extra conditions go in ON. Put them in WHERE and it silently becomes an inner join.
5Zeros exist on purpose: 32 dormant wallets, 2 merchants with no sales, 4 agents with no top-ups. If a total comes back short, that is why.
