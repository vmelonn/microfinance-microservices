00The wire path

One request crosses three protocols. Each boundary exists because the thing on the other side of it speaks a different language.

Why one SOAP hop, and only one

SOAP is not used because it is pleasant. It is used because ACE is an integration broker whose entire purpose is mediating between protocols, and its native contract is a WSDL. Putting SOAP anywhere else in the platform would add XML ceremony to calls that gain nothing from it. Confining it to exactly the boundary where it earns its place means swapping the implementation behind it is one environment variable.

Split along ownership, not along layer count. The question at each boundary was "who is allowed to change this without asking anyone".

iso8583-adapter runs one replica, deliberately

Each pod derives per-transaction PIN keys from its own persisted HSM base key. Two replicas hold different keys, so a PIN block encrypted by one cannot be decrypted by the other, and the failure would look like sporadic DE 39 = 55 declines rather than anything pointing at replica count. Scaling this out needs a shared KMS-backed key, not a higher number in the Deployment.

Two boundaries worth defending

The gateway is separate from the orchestrator because merging them would drag saga machinery into the balance-inquiry path that never uses it, and make the saga coordinator reachable from the internet.

The adapter is separate from everything because it is the only service holding key material and the only one speaking a non-HTTP protocol downstream. Isolating it makes the PCI-relevant scope one pod with one ServiceAccount, instead of smeared across the service that also talks to risk, the ledger, and the gateway.

The shared library, and what stays out of it

libs/mfcommon holds things that must be byte-identical across services: the ISO 8583 codec, SOAP envelope handling, JWT primitives, PIN blocks, audit masking, the resilient HTTP client. If the adapter and the stub disagree about BCD padding by one nibble, every message corrupts.

Business rules deliberately stay out. Risk thresholds live in risk-service; accounting rules live in ledger-service. A shared library that accumulates business logic is how a microservice split quietly becomes a distributed monolith, every service redeploying because one service's rule changed.

02The SOAP boundary

One WSDL, three operations, two implementations. The contract was written first, and that is what makes the implementations swappable.

OperationMTIPurpose
authorize0200 → 0210Financial authorization. Blocks until the switch answers or the gateway's timeout expires.
reverse0400 → 0410Reversal advice. Idempotent at the switch, so safe, and required, to retry until acknowledged.

Why the PIN block is hex

DE 52 is eight bytes of ciphertext containing arbitrary byte values, and several of those, 0x00, 0x08, 0x0B, 0x0C, 0x0E, 0x1F, are illegal in XML 1.0. Not awkward to escape: forbidden, with no escape sequence that makes them legal.

The monolith passed DE 52 as latin-1 text, which works fine over a raw socket. Doing the same across XML produces a document that fails to parse roughly one time in twenty, depending on the ciphertext. Hex-encoding at this boundary makes it always safe, and readable in a trace. ACE's ESQL turns it back into bytes with CAST(… AS BLOB) before the DFDL serializer writes the field.

Three design choices in the codec

Hand-rolled, not zeep. zeep compiles the WSDL at client construction, so process startup acquires a hard network dependency on ACE being reachable, an ACE restart would cascade into the adapter failing its readiness probe. The contract is three operations; it needs to be obvious and to fail loudly, not to be inferred.

Absent fields are omitted, never sent empty. In ISO 8583 an absent data element and a present-but-empty one are different messages, the bitmap bit differs, and a real switch answers the second with DE 39 = 30, format error.

Faults are checked before the status code. A SOAP fault arrives as HTTP 500 with a well-formed body, and some stacks return faults as HTTP 200. Branching on status alone either retries a transaction the switch explicitly refused, or parses a fault as success. And SOAP 1.1 fault children are unqualified, a parser looking for them in the envelope namespace finds nothing and reports a fault with no message.

Fault categoryReached the switch?Caller must
VALIDATIONnoNever retry, the identical request fails identically.
SWITCH_DOWNnoFail cleanly. No reversal needed; nothing was authorized.
SWITCH_TIMEOUTunknownReverse, skip the ledger, flag for reconciliation.

ace-stub is a stand-in, not a mock

A mock returns canned responses. ace-stub genuinely maps the SOAP request onto an ISO 8583 field dictionary, builds real BCD-packed binary with a real bitmap, opens a real TCP socket, frames with a real MLI, correlates the response by STAN, and parses the real binary answer back. The bytes on the wire are the bytes ACE will produce.

That is what makes the integration tests survive the swap: they assert on the WSDL contract, not on either implementation. 

# the entire migration, once entitled
ISO8583_SOAP_ENDPOINT=http://ace:7800/Iso8583Gateway

The conformance obligation

ISO8583.xsd and mfcommon/iso8583/parser.py are two independent implementations of the same binary format. They will drift, not might, unless something forces them together. tests/e2e/test_dfdl_conformance.py is that forcing function: 23 assertions pinning the byte-level properties the DFDL schema declares.

Pinned propertyWhat breaks without it
MTI is 2 bytes BCDEvery message misaligns from byte 2.
Bit N ⇄ DE NOff-by-one shifts every field in the message.
Odd numerics get a trailing FVendor-specific. Some processors pad leading; a mismatch shifts by one nibble.
LLVAR length counts digitsThe most common ISO 8583 parsing bug. 16 digits, LL=16, 8 bytes.
DE 37 is text, not BCD12 characters in 12 bytes, not 6.
DE 52 and 64 are never trimmedCiphertext ending in a whitespace byte loses key material.
MLI is 2 bytes big-endianFraming desynchronises and the connection dies.

What it does not prove: that the DFDL schema parses. That needs an ACE runtime. The first deployment is still the first real test of that file, and the README says so.

04The saga

In the monolith, an exception unwound everything. Across four databases, there is nothing to unwind with, so every step carries a named compensation.

The order is chosen, not arbitrary: cheapest and most reversible first, so that everything undoable happens before the one thing that is not.

Step failsRetriesCompensation
risk evaluate, timeout or 5xx0Fail closed. A risk service that is down must not become one that approves everything.
authorize, DE 39 ≠ 000Decline. Nothing downstream runs.
authorize, timeout0Reversal issued; outcome unknown; no ledger posting.
ledger, duplicate RRN, Not an error. already_recorded, return the original result.
ledger, 5xx after an approval3Compensating 0400. If that also fails: requires_reconciliation and a human.
registration, account creation fails0Delete the user. Otherwise a failed signup leaves someone who can log in, owns nothing, and whose phone number blocks a retry.

05Where money comes from

Double-entry bookkeeping will not let value appear from nowhere. That constraint is the whole design of this section, and ignoring it is what produced the platform's most embarrassing bug.

The bug this fixed

Every customer balance in the platform was negative. Not a display fault. Every posting is a debit and a credit on existing accounts, customers were only ever on the debit side, and nothing ever credited them, so balances could only fall. The demo database showed the entire customer base thousands in debt.

The funding account

Crediting a customer requires debiting something. That something is a system account, acc_system_funding, and it is the only account permitted to go below zero.

Its balance is negative by design, and its magnitude is exactly the float customers are holding. That is not a number to fix. It is the figure a treasury team reconciles against the real bank account backing the wallet, and the scenario run at the bottom of this page shows the two sides agreeing to the cent.

A top-up deliberately does not touch the switch. It models an agent cash-in: somebody hands over money and the wallet is credited, and there is no card being charged to authorise. A card-funded top-up would be a real ISO 8583 transaction with processing code 21, running the same saga as a purchase. The PIN is absent for the same reason: a PIN authorises money leaving an account. What still has to be proven is that the card belongs to the caller, and it is.

Solvency is enforced by the database, not by Python

The obvious implementation, read the balance and then post if it is sufficient, is wrong. Two concurrent spends can each read the same sufficient balance and both post. The check therefore happens inside the same transaction as the insert, holding a row lock: 

# ledger-service, _assert_solvent, called from inside record_posting
if self.db.is_postgres:
    cur.execute("SELECT type FROM accounts WHERE account_id = %s FOR UPDATE", (account_id,))
# ... sum the entries, then:
if current - amount_cents < 0:
    raise InsufficientFunds(account_id, current, amount_cents)
SQLite does not give this for free

The first version of this assumed SQLite's writer lock made the read-then-write safe. It does not. Python's driver starts a transaction at the first INSERT, not the first SELECT, so the balance check ran in autocommit, outside the transaction entirely. Ten threads spending one balance: four succeeded. Database.transaction() now opens with BEGIN IMMEDIATE, which takes the write lock up front. Removing it again and rerunning is how that was confirmed rather than assumed: 8 of 10 rounds overdrew, one as far as -70000 cents.

Two checks, and only one of them is the guarantee

ledger-service, authoritative

Atomic, inside the posting transaction. This is what makes an overdraft impossible. It answers with HTTP 409, which is deliberately distinct from the 422 for a nonexistent account, because the saga treats them differently.

transaction-service, courtesy

A pre-check before the switch is contacted. Racy by nature and not relied upon. Its only job is to stop an unaffordable purchase producing a real authorisation that then has to be reversed.

The pre-check runs before the risk evaluation, not after. Risk is stateful: evaluating records an attempt, which is why it is never retried. Handing it a transaction that was never going to proceed means a customer tapping "pay" on an empty wallet inflates their own velocity counter and sends their next funded transaction to review.

The cost of that ordering

It is a real trade, not a free win. Attempts declined for insufficient funds never reach risk-service, so somebody hammering a drained account is invisible to the velocity rules. That is acceptable here because an empty account is not worth attacking, but it would not be acceptable on a credit product, where the same ordering would hide exactly the behaviour you want to catch.

The invariant

Account typeMay go negativeMeaning if it does
checking, a customernoA bug. Money was created.

Summed across every account, the two always cancel. That is the is_balanced() check, and it is asserted at the end of the scenario run below.

06The third outcome

The single most important difference between this platform and the monolith it came from.

A function call either returns or raises. A network call has a third possibility: it succeeded, and the response was lost. The switch approved, the cardholder is debited, and the caller has no way to know.

A timeout is not a decline

Reporting "declined" for a lost response is a lie that quietly takes someone's money. Reporting "approved" invents a transaction that may never have happened. Neither is acceptable, so the platform carries a third value all the way to the client.

outcomeLedger writtenReversalClient sees
approvedyesnoSuccess, with an RRN and an authorization ID.
declinednonoA specific reason, decoded from DE 39.
reversednoyes, acknowledgedThe authorisation happened and was undone. No money moved.
unknownnoattempted, not acknowledgedrequires_reconciliation: true. Do not blindly retry.

The reasoning behind "no ledger write" is asymmetric, and worth stating plainly: a posting for a transaction that never happened invents money and nothing will ever catch it. A missing posting for one that did happen is caught the next day, when reconciliation compares the ledger against the switch's own settlement file and finds an RRN in one and not the other. One error is silent and permanent; the other is loud and temporary.

A bug the solvency work exposed

When the ledger refused a posting, the saga compensated correctly with a reversal, but the response still said status: "approved" with ledger_status: "reversed" buried inside it. A client reading the field it is supposed to read was told the payment succeeded when no money had moved. Overdraft protection made that path reachable for an ordinary reason rather than only during an outage, which is how it surfaced. reversed is now a top-level outcome of its own. 

# transaction-service, step 4
if auth["outcome"] == "unknown":
    log.error(f"UNKNOWN outcome rrn={rrn}, no ledger posting")
    return TransactionResponse(
        status="unknown",
        rrn=rrn,
        requires_reconciliation=True,
    )

07Cycles

Correlation IDs

In the monolith one purchase was one call stack, and a traceback told you everything. Here it is seven log streams on seven pods. The gateway mints a correlation ID, every service propagates it unchanged, through the SOAP hop, via a header inside the envelope, and every log line carries it.

Two identifiers, deliberately distinct: the correlation ID exists for requests that never become transactions (a declined risk check, a 401) and lives as long as the logs; the RRN exists for money that moved and must be findable in seven years.

Cross-replica idempotency

The claim is taken at the gateway, before any downstream work, via an atomic Redis SET NX. Claiming inside the orchestrator instead would still let two concurrent duplicates both pass risk evaluation before either claimed, and since evaluating records an attempt, the retry would count twice against the velocity window.

docker-compose runs two gateway replicas specifically so this is observable. A single-replica compose file hides the entire class of bug the Redis layer exists to prevent.

Velocity across pods

A Redis sorted set per card: ZADD records the attempt, ZREMRANGEBYSCORE prunes the window, ZCARD counts. With per-pod memory instead, six attempts spread across three replicas look like two attempts each and every one is approved, the fraud control silently stops working while nothing appears wrong.

Analytics sync

Hourly, watermark-driven, and it reads through /internal/ledger/export rather than querying ledger-service's Postgres directly. Reaching into another service's tables is faster and is the single most common way a microservice architecture collapses back into a shared schema, the moment this job selects from ledger_entries, that table can never change without breaking a job its owner does not know exists.

Why the watermark is a correctness requirement

ClickHouse's ReplacingMergeTree deduplicates eventually, at background merge time, so re-loading a row is safe for the fact table. But the mv_daily_volume materialized view fires on INSERT, before that deduplication, so a re-load double-counts in the aggregate even though the fact table self-corrects. Advancing the watermark only after a confirmed batch is what keeps the aggregates honest, not merely what makes the sync fast.

The CronJob also sets concurrencyPolicy: Forbid for the same reason: two overlapping runs would read the same watermark and double-count everything between them.

08Scenarios

Every flow below was produced by running the platform. The steps marked observed are lines the services themselves logged, matched on the correlation ID the gateway minted for that request.

What this section used to be

It claimed to be a recording and was half of one. The outcomes were real, but the per-layer steps were written by hand, and in the purchase flow three of them ran before the request was sent: 

sc.step("api-gateway", "claim the idempotency key")
sc.step("transaction-service", "resolve card, prove ownership")
sc.step("risk-service", "velocity, amount and entry-mode rules", "approve")

status, body = purchase(user, 25.50)   # the call happens HERE

So the page asserted that risk-service approved a transaction that had not been sent. Worse, one of those steps described work that emits no evidence at all: a fresh idempotency claim was not traced, only the replay branch was. If a layer had stopped participating, the documentation would have gone on describing it.

Fixing it turned up two more defects. Log timestamps had one-second resolution, so a five-service flow could not be ordered and two adapter lines were first shown in the wrong order. And trace.emit returned early when Redis was absent, so every trace point vanished in exactly the environments that have no Redis.

scripts/scenarios.py boots all eight services, drives each situation from outside as a mobile client would, then reads back every log line carrying that request's correlation ID. Regenerating this section means re-running the platform, so a flow cannot drift from the code. 

python scripts/scenarios.py                  # boot, run, tear down
python scripts/scenarios.py --base $ROUTE    # outcomes only, pod logs are out of reach
python scripts/scenarios.py --only risk      # one group

Probes, every service

/health is liveness: is this process responsive? It deliberately does not check downstreams, a liveness probe that fails during a dependency outage makes OpenShift restart healthy pods, losing in-flight work and fixing nothing.

/ready is readiness: should this pod receive traffic? This one does check dependencies. The adapter's readiness runs a genuine echo test through ACE and out to the switch, because a pod that answers while the switch is unreachable gets traffic it can only fail.

10Data ownership

Four stores, three owners. The boundaries are about who may migrate a schema, not about how many processes are running.

StoreOwnerHoldsIf lost
Postgres · authauth-serviceusersUnrecoverable. Real backups required.
Postgres · ledgerledger-serviceaccounts, cards, transactions, ledger_entriesUnrecoverable. This is the money.
Redisgateway + riskIdempotency claims, velocity windowsTolerable. Both are TTL'd derived state; the ledger's PRIMARY KEY is the real backstop.
ClickHouseanalytics-syncfact_transactions, rollupsRebuildable, rerun the sync with an empty watermark.
No foreign key crosses a service boundary

accounts.user_id references a user that lives in auth-service's database, and there is deliberately no FK behind it. Referential integrity across a service boundary cannot be enforced by a database; it is enforced by the fact that only auth-service creates users. Adding a cross-database FK is how a microservice split ends up with a shared schema and two services that can no longer deploy independently.

The one guarantee

Everything upstream, the gateway's idempotency claim, the saga's retry policy, the reversal on timeout, is best-effort. The guarantee that cannot be wrong is PRIMARY KEY (rrn) on transactions: one atomic statement, enforced by the database, holding however many replicas race. Ten threads released simultaneously on one RRN produce exactly one posting and nine already_recorded responses.

Network policy

Default deny, then specific paths re-admitted. Without it every pod can reach every other pod, and isolating the adapter as the sole holder of key material means nothing, any compromised pod could simply call it.

FromMay reach
OpenShift routerapi-gateway only
api-gatewayauth, transaction, ledger, not risk or the adapter
transaction-servicerisk, ledger, adapter
iso8583-adapterace-stub / ACE only
ace-stub / ACEthe switch only

The gateway deliberately cannot reach risk-service or the adapter directly. Those are the orchestrator's to call, and letting the edge reach them would route around the saga.

Arbitrary UIDs

OpenShift assigns a random UID at runtime, not the image's declared user. Every Dockerfile installs packages system-wide rather than into a named user's home and runs chgrp -R 0 /app && chmod -R g=u /app, because whatever UID gets assigned is always a member of GID 0.

It does not look like a permission error

Getting this wrong surfaces as executable file not found in $PATH. The file genuinely exists; the assigned UID just cannot read the directory it was installed into, and the error sends you looking in entirely the wrong place.

Before production

  1. Real secrets. The base ships a placeholder Secret so a fresh cluster applies cleanly. Applying it as-is deploys a published JWT signing key.
  2. Repoint SWITCH_HOST. The prod overlay deletes host-simulator; if the address still names it, every transaction fails.
  3. Pin image tags. latest means a pod restart can pick up a different build than its neighbours.
  4. Back up HSM_MASTER_KEY_HEX somewhere that is not this cluster. Losing it makes every persisted PIN block permanently undecryptable.

Honest costs

The decomposition is not free, and the main price is the unknown state. In the monolith it could not occur, a function call either returned or raised. Here it is a real outcome that needs a reversal, a reconciliation queue, and eventually a human.

Second: latency. Seven hops instead of seven function calls. Third: seven deployables, nine images, and a NetworkPolicy graph to keep correct. Fourth: local development now needs a container runtime instead of uvicorn.

What it buys is genuine: risk thresholds retune without redeploying the ledger, the gateway scales independently of the crypto edge, and the PCI-relevant surface is one pod instead of one process.

Known gaps

  • No MAC on outbound messages. DE 64/128 are modelled and masked but never generated.
  • DE 90 placeholders in reversals, the simulator only needs MTI and STAN.
  • No RBAC. Any authenticated user is equivalent to any other.
  • MockHSM is XOR, not a real HSM. Correct interface, no tamper resistance.
  • Plaintext PIN crosses one internal hop, gateway to adapter. Mitigated by NetworkPolicy; a real PCI environment wants mTLS.
  • RRN collision is possible, 1 in 100 within the same second. The PRIMARY KEY turns it into a rejected duplicate rather than corrupted money, but the format should change before real volume.
  • ACE artifacts are unverified. Written, never compiled or run.
