1. Account

Your number is your account. Any format works.
A merchant must exist before any purchase can be credited.

2. Top up

Every wallet starts at zero, and a purchase that would take it below zero is refused. So money has to get in first.

A top-up is an ordinary double-entry posting, not a special case: the acc_system_funding account is debited and yours is credited. That account therefore runs negative, and its magnitude is exactly the float customers are holding. It does not go near the switch, because there is no card being charged, only cash handed to an agent.

3. Pay

Filled in by Register. Logging in does not fill it: that proves who you are, and the API deliberately never hands out card numbers, so the console cannot look yours up.
Credits merchant:demo, a single hardcoded merchant. A real acquirer would take the payee from DE 42 on the transaction; this platform inherited the shortcut from the monolith.

Pay twice with the same key to see the cached reply and an unchanged balance. That is the guarantee, not a caching detail.

Spending more than you hold is declined before the switch is called, so there is no approved authorisation left to reverse.

5. Send to another user

Send to a phone number, the way a mobile wallet works. A different path from a purchase: processing code 400000 instead of 000000, and the recipient travels in DE 103 rather than crediting the merchant. An account ID or card number also resolves, since the ledger tries card, then account, then phone.

Operational ledger (live, Postgres)

Reset deletes every posting and returns all balances, including the funding account, to zero. Accounts, cards and logins survive, so you keep the wallet you are signed in as.

Empty everything also deletes accounts, cards and users, across both databases. Nothing is left to log in as, so you will need to register again. Type the confirmation to run it.

Both are refused unless the environment permits them: ALLOW_LEDGER_RESET=1 and ALLOW_AUTH_PURGE=1, set in dev and not in prod.

Analytics (ClickHouse, read-only SQL)

Free-form SQL runs against ClickHouse, never the ledger. ClickHouse is derived and can be rebuilt from Postgres, so a bad query costs nothing. It also lags the ledger by up to the sync interval.
